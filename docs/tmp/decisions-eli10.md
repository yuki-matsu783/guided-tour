# 判断をお願いしたい3つのこと

## まず、この拡張機能がしていること

この拡張機能は、Web サイトの上で「ここを押してね」と**指で差して教える先生**のようなものです。

- 先生が使う台本が「ツアー」です。ツアーには、手順ごとに「どの部品を指すか」が書いてあります
- 先生は台本を読んで画面の中から部品を探し、見つけたら枠で光らせます（ハイライト）

いちばん大事な決まりは次のとおりです。

> **自信がないときは指さない。間違った場所を指すより、「文章だけで説明する」ほうがまし。**

間違った場所、たとえば「保存」のつもりで「削除」を光らせると、受講者はそれを押してしまうかもしれないからです。

### 部品の探し方（5つの段階）

台本には、探すための手がかりを書けます。強い順に5つあります。

| 段階 | 手がかり | たとえると |
|---|---|---|
| 1 | ID（開発者が付けた目印） | 名札 |
| 2 | 役割と名前（ボタンで、名前が「保存」） | 「保存」と書いたボタン |
| 3 | ラベル（入力欄の横の「メールアドレス」） | 入力欄の見出し |
| 4 | 表示文字列（画面に見えている文字） | 書いてある文字 |
| 5 | CSS（画面の構造） | 「2階の3番目の部屋」のような住所 |

先生は段階1から順に試し、**ちょうど1つに決まった段階**の答えを使います。
2つ見つかったら「どっちか分からない」ので、その段階は使わずに次の段階へ進みます。

## 1. within（探す範囲）の形

### within とは

画面に「削除」ボタンが2つあるとします。

```
┌──────────── ページ ─────────────┐
│ 一覧                             │
│  ・ファイルA  [削除]  ← ①        │
│                                  │
│  ┌──── 設定ダイアログ ────┐      │
│  │  危ない操作            │      │
│  │  [削除]  ← ② 指したい   │      │
│  └────────────────────────┘      │
└──────────────────────────────────┘
```

「削除ボタン」とだけ書くと①と②の2つが見つかり、どちらか決まりません。
そこで「**設定ダイアログの中で**探して」と、探す場所を区切ります。これが within です。区切った中なら②だけに決まります。

### 見つかった問題

今の作りでは、段階1（名札）と段階4（文字）が within を無視して、ページ全体を探しています。
そのため「ダイアログの中に無いなら、外の①を使おう」となることがあります。これは「間違った場所を指さない」に反します。

原因は、承認済みのテストケース T-LOC-30 の文面です。「段階2では範囲が見つからず失敗しても、範囲を持たない段階4は試される」と書いてありました。
ところが台本の書き方では、within は手がかり全体に1つしか書けません。「範囲を持たない段階」というものが、そもそもありません。

### 選択肢

**A. within を1つだけ書き、全部の段階に効かせる**（書き方は今のまま）

```yaml
target:
  within: { role: dialog, name: [設定] }   # 全部の段階がダイアログの中だけを探す
  testId: delete-btn
  role: button
  name: [削除]
  text: [削除]
```

- ダイアログが見つからなければ全段階が失敗し、「文章だけの案内」になる
- 分かりやすく安全。ただし「この段階だけは別の場所で探したい」は書けない

**B. 段階ごとに範囲を変えられる**（汎用的な形）

```yaml
target:
  within: { role: dialog, name: [設定] }   # ふつうはダイアログの中を探す
  testId: delete-btn                      # → ダイアログの中で探す
  role: button
  name: [削除]                            # → ダイアログの中で探す
  text:
    values: [削除]
    within: { css: "#danger" }            # → この段階だけ別の場所で探す
  css:
    values: ["#app .del"]
    within: page                          # → ページ全体で探す（はっきり書いたときだけ）
```

- 段階ごとに、探す場所を変えられる
- ページ全体を探すのは、作者が `within: page` と書いたときだけ。範囲が見つからないときに、勝手に全体へ広げることはしない
- 書き方が少し増える。決めた理由を ADR に1枚残す

| | A | B |
|---|---|---|
| 間違った場所を指す危険 | 低い | 低い（全体は明示したときだけ） |
| 書き方の簡単さ | 簡単 | 少し増える |
| 柔軟さ | 低い | 高い |
| 後から変える費用 | いまは同梱ツアーが自己紹介だけなので、どちらに決めても今が一番安い | 同左 |

おすすめは **B** です。サイトの作りは変わりやすく、段階ごとに逃げ道を書けるほうが、台本を長く使えるからです。

## 2. role だけの手がかり

### 前提: 役割と名前

画面の部品は、それぞれ次の2つを持っています。

- **役割**: ボタン・リンク・入力欄など、「何をする部品か」
- **名前**: 「保存」「削除」など、目の見えない人向けの読み上げソフトが読む呼び名

段階2は、この**2つを組み合わせて**探す段階です（「ボタンで、名前が『保存』のもの」）。

### 問題

今は、役割だけを書いて名前を書かないこともできます。

```yaml
target:
  role: button      # 名前を書いていない
```

これは「名前は何でもいいから、ボタンが1つだけならそれ」という意味になります。

```
作者が想定した画面:  [保存]           → 保存が光る（ねらいどおり）
画面が変わった後:    [削除]           → 削除が光る（危ない！）
```

画面が変わってボタンが入れ替わっても、ボタンが1つでありさえすれば、それを指してしまいます。

### 選択肢

- **名前を必ず書かせる**（おすすめ）: role を書いて name が無いと、取り込むときにエラーになる。「ボタンであること」だけを条件にしたいときは、`require.role`（候補を絞る条件。単独では探さない）を使う
- **書けるが警告を出す**: 取り込めるが、「間違った案内につながりやすい書き方です」と警告が出る

## 3. ログの検査の順番

### 前提1: ログと安全装置

ログは、あとで不具合を調べるための「日記」です。
ただし、この日記に**ページの文字や URL を書いてはいけない**決まりがあります。個人の情報や秘密が混ざるかもしれないからです。

そのため、日記に書けるのは、出来事ごとに決めた項目（数・種類・内部の番号）だけです。
決めていない項目を渡されたら、中身は捨てて「おかしな書き込みがあった」（`logger.invalid`）とだけ書きます。

### 前提2: ログのレベル

日記には「どれだけ細かく書くか」の設定があります。

```
エラー  ＜  警告（ふだんの設定）  ＜  情報  ＜  詳細
```

ふだんは「警告」なので、「詳細」の出来事は書きません。

### 食い違い

開発者が「詳細」の出来事に、うっかり URL を入れてしまったとします。

| 順番 | 何が起きるか |
|---|---|
| **検査を先にする**（承認した既定の解釈） | 書かない出来事でも、先に中身を確かめる。「おかしな書き込みがあった」と残るので、**間違いにすぐ気づける** |
| **レベルを先に見る**（承認した T-LOG-25 の文面） | 書かない出来事は確かめずに捨てる。何も残らない。設定を「詳細」にした日に初めて気づく |

どちらでも、**URL が日記に書かれることはありません**。違いは、間違いに早く気づけるかどうかだけです。

おすすめは **検査を先にする** です。安全装置は、使わないときも点検しておくほうが安心だからです。
