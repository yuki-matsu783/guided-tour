# 自己紹介ツアーの案

YAML 本体と Markdown は書かない。利用者の承認後に `public/tours/<id>/` へ実装する。

## 方針

- 初めて使う人が、一覧から開始し、拡張機能の使い方を操作しながら学ぶ。
- サイドパネル、設定、取り込みの説明は拡張機能自身の画面にあり、ページ側の表示では指せない（`chrome-extension://` は `origins` に書けない）。これらは `kind: guide`（案内だけの手順）で、文章だけで案内する。
- ページ上の表示（ミニガイド・ハイライト・吹き出し・完了の目安）は、http/https の実在ページで体験させる。
- 拡張機能はページを自動で開かない（FR-33, 87）。最初のページ手順で、「今のタブで開く」「新しいタブで開く」「既存のタブを使う」を押す体験自体を手順にする。
- 完了の目安は移動を制限しない（FR-62）。この体験も手順にする。

## 体験に使うページの比較と推奨

| 候補 | 利点 | 欠点 |
|---|---|---|
| `https://example.com/` | 短い固定のページ。見出し1つとリンク1つで、ハイライトの対象が明確。広く知られ、到達できる環境が多い | 外部ページ。リンクの表記が変わりうる（「Learn more」、旧表記「More information...」）。社内で外部への通信が遮断される環境がある |
| `https://example.org/` | `example.com` と同じ内容（IANA 管理） | 同上。社内の遮断で `.com` と同じ扱いになりやすく、利点がない |
| `https://www.iana.org/help/example-domains` | 説明の文章が長く、スクロールの体験に向く | 構造が複雑で、見出し・リンクが多く、特定が不安定。変更されやすい |
| 拡張機能の同梱ページを `web_accessible_resources` で公開（`chrome-extension://`） | 到達できなくなる心配がない | `origins` は http/https のみで、ページ側の表示を描けない（C-09）。体験できない |

推奨は **`https://example.com/`**。理由は、構造が最小で、表記の変更を名前の候補（複数）で吸収しやすく、`origins` を1つにできるため。`example.org` を併記しても到達できる条件は変わらないので、採用しない。

### 外部ページに頼る危うさと、体験が壊れないことの根拠

| 危うさ | 対処 |
|---|---|
| リンクの表記が変わる（「Learn more」から旧表記、または別の語） | `name` の候補を複数持つ（`Learn more`、`More information...`、`More information`）。見出しは `Example Domain`。それでも見つからなければ、8秒で文章だけの案内へ切り替わり、「次へ」で進める（FR-80、NFR-04）。見つかればハイライトに変わる |
| 構造が変わり、見出しが無くなる | 同上。説明文は、ハイライトが出なくても手順を理解できる書き方にする（FR-19 の考え方）。ハイライトが出ない場合の読み方を、本文に1行入れる |
| 到達できない環境（遮断、オフライン） | ページが開かず、役割のタブが URL 条件に合わない状態になる。「ページ上の表示」は出ないが、サイドパネルの手順と「次へ」は動く。案内だけの手順は影響を受けない。ステップの一覧から任意の手順へ移れる（FR-55） |
| 開始時に example.com への許可を求められる | 導入前の説明に書く（ステップ1の本文）。拒否すると開始されない（FR-26）。この仕様は変えない |
| リンクを押すと別のオリジン（iana.org）へ移り、URL 条件に合わなくなる | 本文で、このツアーではリンクを押さないよう書く。押した場合は、正しいページへ戻す手段が出る体験になり、本文でそれも説明する（FR-91） |

## ツアーの概要

| 項目 | 案 |
|---|---|
| ID | `guided-setup-tour-intro` |
| schemaVersion | 3 |
| name | Guided Setup Tour の使い方 |
| description | サイドパネル、ミニガイド、ハイライトと吹き出し、完了の目安、ステップの移動、表示の切り替え、一時中断と終了、ショートカットキー、取り込み、設定を、操作しながら 10 分ほどで学びます |
| minExtensionVersion | 同梱時の拡張機能のバージョン（ミニガイドなど最新の機能を使うため） |
| origins | `https://example.com` |
| 置き場 | `public/tours/guided-setup-tour-intro/tour.yaml`、`steps/*.md`。画像は、サイドパネルの見方（ステップ1）と、ミニガイドの3つの表示状態（ステップ3）に任意で使う（代替文を必須とする） |

### tabs

| 役割 | label | open | url（URL 条件） |
|---|---|---|---|
| main | 練習用のページ（example.com） | `https://example.com/` | origin: `https://example.com`、path: exact `/` |

- 「今のタブで開く」「新しいタブで開く」が `open` を使う。ページの手順は `tabs.main.url` を継承するので、各ステップには `url` を書かない（`kind: page` は役割の URL 条件で足りる）。

## ステップの一覧（12 ステップ）

ページの手順は 2〜7（6 ステップ）、案内だけの手順は 1、8〜12（6 ステップ）。案内だけの手順に入ると、ページ上の表示とミニガイドは消える。「戻る」でページの手順へ戻ると復帰する。この性質も本文で触れる。

### 設計上の注意

- 手順 4・5・6 のハイライトは、`example.com` の内容に依存する。手順 4 は見出しだけに頼る。5・6 は表記が変わりうるリンクを使い、`name` の候補を3つ持つ。見つからない場合は、8秒で文章だけの案内に切り替わり、「次へ」で進める（FR-80）。この場合、保守記録に「未検出」が残り、一覧の「要確認」が付く。**自己紹介ツアーが「要確認」になる**ことは、利用者の判断が要る（下の課題）。
- 手順 2 は、タブ未対応の状態で入る（役割のタブが無い）。サイドパネルに手段の一覧が出る体験が、そのまま内容になる。
- 手順 4・5 で必須の照合（`require`）を書き、取り込み時の警告（FR-10）を避ける。
- 手順 3・7 は対象要素を持たない `kind: page`。ミニガイドは出る（URL 条件に合うページのため）。
- 手順 6 の `done` は、状態（`state`）を持つ入力欄が example.com にないため、`type: element`（出現）を使う。`filled` などの状態は体験できない。説明文では「入力済みなど他の種類もある」と1行触れるだけにする。
- `type: page` の完了の目安（FR-63）は、手順 2 でのみ使う。完了ページの体験（URL が変わって不一致にならない）は、example.com に URL を変えられる操作がなく、体験できない。
- 画像は、サイドパネル内の画面の説明（手順 1・9・10・11）に使うと分かりやすいが、必須ではない。拡張機能の画面が変わると古くなるため、**画像を使わない**案を推す。
