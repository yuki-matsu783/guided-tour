# 機能を作る進め方と、人が判断する場面

## 順序

1. 計画：触る領域の要件書・設計書・ADR を先に読む。似た実装が既にあれば、まず探してそれに倣う（毎回ゼロから流儀を考えない）
2. テスト：先に**テストケースの一覧（説明文だけ、中身は空）**を利用者に出し、承認を得てから実装する
3. 実装：テストを通す。通ったら振る舞いを変えない範囲で整理する
4. レビュー：差分を別の目（別のエージェントなど）で見る。書いた本人には自分の問題が見えにくい
5. 検証：コミット前に `pnpm run typecheck`・lint・`pnpm run test` を通す。`package.json` の scripts にあるものを使う
6. コミット：区切りがつくたびに積む。1機能で1回にまとめない

## 計画の置き場

計画は `docs/tmp/` にスナップショットとして置く。陳腐化する前提で、最新に保たない。
残す価値があるものは要件書・設計書・ADR に移す。

## 利用者が判断する4つの場面

次のときは、自分で決めずに利用者に確かめる。

| 場面 | 発火するとき | 利用者が決めること |
|---|---|---|
| A | 承認済みのテストケースを変えたい（削る・意味を変える） | 変更を認めるか。理由を添えて止まる |
| B | 実装して、設計の方針を変える必要が出た | 方針を変えるか。変えるなら ADR を書いてから進む |
| C | レビューが重大な指摘を出した | いま直す／理由つきで先送りする／リスクを受け入れる |
| D | 書いたコードが既存の ADR と食い違う | 解釈を決める。新しい ADR に解釈を書いてからコミットする |

- B と D の ADR は、その判断を含むコミットより前に書く。ADR はコミットの成果物ではなく前提
- 既存の ADR の本文は書き換えない（[書き分け](docs-writing.md)）
- 判断待ちで作業全体を止めない。判断を要しない部分は先に進める
